# Project setup

Everything needed to turn this folder of Swift files into a project that builds,
runs and installs. Written for someone who has never seen the project.

There is deliberately **no `.xcodeproj` in this repository**. A project file
generated by hand, never opened in Xcode, is worse than none — it fails in ways
that look like your mistake rather than its. Twelve minutes of the steps below
produces one you can trust.

---

## 1. What you are building

An internal iPhone app that reads and writes Outlook tasks in this
organization's Intermedia Hosted Exchange 2016 mailbox over EWS, including
Outlook Categories and their colors. Not a public App Store product.

Today it runs fully against `MockBackend`. The network layer does not exist yet;
`BEFORE-EWS.md` covers what is known about the server and the order to build it
in. **Get the app compiling and running on a device against the mock before
writing a single line of SOAP.**

Requirements: a Mac with Xcode 16 or newer, an Apple Developer account, and a
physical iPhone. The simulator is fine for most work but cannot do Face ID
enrollment realistically or hold a real Keychain item, so the unlock modes need a
device.

---

## 2. Create the project

1. Xcode → **File → New → Project → iOS → App**
2. Fill in:
   - **Product Name:** `TaskPerfect`
   - **Interface:** SwiftUI
   - **Language:** Swift
   - **Storage:** None — the SwiftData container is built in code
     (`TaskPerfectApp.swift`), and letting the template add its own produces two
     containers fighting over one store
   - **Testing System:** XCTest (see §7)
3. Delete the generated `ContentView.swift` and `TaskPerfectApp.swift`. The real
   entry point is `App/TaskPerfectApp.swift` from this folder.
4. Drag these into the project navigator — **Copy items if needed** checked,
   **Create groups** (not folder references):
   `App/`, `Domain/`, `Backend/`, `Persistence/`, `Features/`, `DesignSystem/`,
   `Support/`, `Resources/`
5. Do **not** add to the app target: `Tests/`, `VerifyEWS/`, or any `.md` file.
   `Tests/` goes in the test target (§7); the rest belong in the repo but not in
   the binary.

---

## 3. Info.plist — read this before you skip it

Xcode 15+ sets `GENERATE_INFOPLIST_FILE = YES` and synthesizes `Info.plist` from
build settings. So dragging in `App/Info.plist` does nothing at all unless you
also point the target at it. **Either route works. Route A is less to explain to
the next person; route B is fewer moving parts.**

### Route A — use the supplied file

1. Target → **Build Settings** → set `GENERATE_INFOPLIST_FILE` to **No**
2. Set `INFOPLIST_FILE` to `TaskPerfect/App/Info.plist`
3. Confirm the bundle identifier, version and build number still come from build
   settings — the supplied plist deliberately omits them

### Route B — keep generation on, add the keys as settings

Leave `GENERATE_INFOPLIST_FILE = YES` and add these under Build Settings (or the
target's **Info** tab):

| Build setting | Value |
|---|---|
| `INFOPLIST_KEY_NSFaceIDUsageDescription` | Task Perfect uses Face ID to unlock your tasks without you retyping your Exchange password. |
| `INFOPLIST_KEY_UISupportedInterfaceOrientations` | `UIInterfaceOrientationPortrait` |
| `INFOPLIST_KEY_UILaunchScreen_Generation` | `YES` |

Then add `ITSAppUsesNonExemptEncryption` = `NO` in the Info tab. Read
`App/Info.plist` anyway — the comments in it explain what is deliberately absent
and why, which matters more than the keys themselves.

### The one that is not optional

`NSFaceIDUsageDescription`. Without it, iOS **terminates the process** the moment
`LAContext.evaluatePolicy` runs, which is the first time anyone chooses biometric
unlock in Settings → Account. Not a denied prompt — a crash. It will not show up
in any simulator run where nobody touches that setting, which is exactly how it
reaches a colleague's phone.

## 4. Assets

`Resources/Assets.xcassets` ships with the accent color set and an app icon slot.
The icon PNG itself is the one thing that cannot be generated from these files —
see `Resources/Assets.xcassets/AppIcon.appiconset/README-ICON.md`. Until it
exists, expect a build error naming `AppIcon`; that is intentional, so a white
square cannot be shipped by accident.

## 5. Build settings that matter

| Setting | Value | Why |
|---|---|---|
| `IPHONEOS_DEPLOYMENT_TARGET` | `17.0` | SwiftData, `@Observable` and the `Tab`-era SwiftUI APIs all require it |
| `SWIFT_VERSION` | `6.0` | see below |
| `SWIFT_STRICT_CONCURRENCY` | `complete` | the code is written for it |
| `TARGETED_DEVICE_FAMILY` | `1` | iPhone only |
| `SUPPORTS_MAC_DESIGNED_FOR_IPHONE` | `NO` | untested, and the Keychain access control behaves differently |
| `ENABLE_USER_SCRIPT_SANDBOXING` | `YES` | the default; nothing here needs to escape it |
| `DEAD_CODE_STRIPPING` | `YES` | default |

**On Swift 6 language mode:** the code was written against it — `LocalStore` is a
`@ModelActor`, `TaskStore` and `Reachability` are `@MainActor`, and the actor
boundary between them is respected deliberately rather than by accident. Two
places in particular exist only because of it and should not be "simplified":

- `LocalStore.pendingChanges()` returns `[QueuedChange]`, a `Sendable` value
  snapshot, rather than the `[PendingChange]` `@Model` objects. Returning the
  models compiles under Swift 5 mode and is a real data race: `ModelContext` is
  not thread-safe, and reading those properties from the main actor touches a
  context owned by another actor. The symptom would be intermittent and
  miserable to find.
- `Reachability.monitor` is `nonisolated(unsafe)` so `deinit` can cancel it.
  `deinit` is never actor-isolated. `NWPathMonitor` is documented as safe to
  cancel from any thread, so the annotation states something true rather than
  hiding something.

If you must fall back to Swift 5 mode to get a first build, treat it as a
temporary measure and note it — not a decision.

No third-party dependencies. Nothing to resolve, no package manifest, no
CocoaPods. Keep it that way if you can: every dependency added to an internally
distributed app is something someone has to re-sign in two years.

## 6. Signing and distribution — decide this before requesting certificates

This is the one open question in the project, and it changes the bundle
identifier, the provisioning profile and the App Store Connect record. Pick
deliberately; all four are viable.

| Route | Review? | Expiry | Cost | Notes |
|---|---|---|---|---|
| **TestFlight internal** | No, for internal testers | **90 days per build** | Standard $99/yr | Fastest to first install. Someone re-uploads every quarter, forever. Up to 100 internal testers. |
| **Custom App via Apple Business Manager** | Yes | None | Standard $99/yr | Private distribution to your organization only; never appears in public search. Requires the org enrolled in ABM. The usual answer for an app like this. |
| **Apple Developer Enterprise Program** | No | Annual re-signing | Separate **$299/yr** | Real eligibility bar — 100+ employees and a D-U-N-S number. Full control, more obligation. |
| **Public App Store** | Yes, full | None | Standard $99/yr | A mail-client-adjacent app with one provider's host baked in will draw reviewer questions. Hard to justify given the audience is one organization. |

Two consequences worth knowing whichever way you go:

- **Demo mode is an unauthenticated path into the UI.** `SignInView`'s *Explore
  with sample data* calls `Session.signIn(credentials: nil)` and opens the app on
  fixture data with no credential check. Harmless — the fixtures are the only
  thing reachable and no network call is made — and useful for demonstrating the
  app without a mailbox. But it is a real door, and if the route chosen is public
  App Store it becomes the path a reviewer takes. Decide to keep it; don't
  inherit it.
- **The fixtures contain realistic internal-looking content** — category names,
  colleague first names, matters that read like actual work. It ships inside the
  binary. Fine internally, worth a glance before any wider distribution.

## 7. Test target

Add one at project creation; retrofitting is more annoying than it sounds.

1. **File → New → Target → Unit Testing Bundle**, named `TaskPerfectTests`
2. Add the files in `Tests/` to that target **only**
3. Set the test target's Host Application to `TaskPerfect`

`Tests/` covers `RecurrenceEngine` and `TaskSorting` — the two pure-function
files where a regression is silent and expensive. They are also exactly what
breaks first when a real `EWSMapper` starts feeding them server data instead of
fixtures, which is the argument for having them before you write it.

**These tests have never been run.** They were written by reading the
implementation, not by executing it. Expect a handful of assertions to need
adjusting on first run — where that happens, the interesting question is always
whether the test or the implementation is wrong, and it is worth actually asking
rather than editing the assertion until it passes.

## 8. First run — what "working" looks like

1. Build and run on a device.
2. Tap **Explore with sample data**. You should get a populated task list with
   seven fixed tabs plus one per category, colored spines on the leading edge of
   each row, and an Overdue section in red at the top.
3. Complete a task by tapping its circle. It should change instantly.
4. Swipe left on a task, confirm the delete, then use Undo.
5. Settings → Categories → rename a category. Every tagged task should follow.
6. Turn off Wi-Fi and cellular, force-quit, relaunch. **The full list must still
   appear** — that is the SwiftData cache doing its job, and it is the single
   most important behavior to confirm before touching the network layer.
7. Still offline, edit a task. Reconnect. The change should push on its own
   without you tapping anything.

If 6 or 7 fails, stop and fix it. Everything in the EWS layer assumes both.

## 9. Then, and only then, EWS

Read `BEFORE-EWS.md` in full. The short version:

- EWS is confirmed enabled on this mailbox — three independent ways.
- Authentication works on the **bare e-mail address**, no domain prefix. Negotiate
  the scheme; do not hardcode NTLM.
- Reading the master category list works, colors intact.
- **Writing** the `CategoryList` item has never been attempted against this
  mailbox. Category colors, renames and deletes all depend on it. Test it third,
  not last — before the category screens are wired to a live backend.
- `Companies` as the *Assigned To* field is an untested round trip. Five minutes.
- Capture real XML from this mailbox as you go. Hosted Exchange deployments differ
  from Microsoft's documentation in small ways that only appear at runtime, and a
  saved response beats the spec every time.

`VerifyEWS/verify.sh` is a connectivity probe for a specific machine on a
specific network — not a gate on whether the project can proceed.

## 10. Version control, first thing

Before any change, so there is a baseline to diff against:

```bash
cd TaskPerfect-project
git init
git add .
git commit -m "Task Perfect: prototype plus Swift foundation, pre-Xcode"
```

`.gitignore` is already in place at the repo root. It keeps `xcuserdata/` out —
otherwise every person's window layout and breakpoints collide in every pull —
while keeping `project.pbxproj` and `xcshareddata/` in, because those *are* the
project.
